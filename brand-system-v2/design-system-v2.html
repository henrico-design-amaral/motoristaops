DESIGN SYSTEM V2

Tokens, temas, padrões de componentes, estados, responsividade e critérios técnicos para transformar as decisões do Brand Book em produtos digitais consistentes.

Status: base canônicaSem sombras/degradêsAcessibilidade: alvo WCAG 2.2 AA
01

Arquitetura

Design System é camada de implementação. Ele não cria uma identidade paralela.

Brand Book → Style Guide → Design System → produto.

Foundation

Cor, tipografia, spacing, radius, grid, iconografia, motion e acessibilidade.

Components

Botões, campos, cards, chips, tabelas, navegação, feedback e padrões de conteúdo.

Patterns

Fluxos, formulários, dashboard, páginas, estados vazios, erro, confirmação e módulos.

Qualquer componente que force exceção recorrente ao Brand Book deve ser revisto no sistema, não normalizado silenciosamente.

#9A3412 no modo claro.

05

Layout responsivo

Breakpoints são ferramentas de layout, não categorias rígidas de dispositivo.

Base

4 colunas. Conteúdo móvel e módulos empilhados.

≥ 48rem / 768

Transição para tablet; 8 colunas quando a complexidade justificar.

≥ 64rem / 1024

12 colunas. Conteúdo pode ganhar regiões paralelas.

≥ 90rem / 1440 é breakpoint de expansão, não autorização para esticar conteúdo. Usar max-width e preservar respiro.
Responsividade reorganiza. Não encolhe tudo para caber.

07

Estados e interação

Estado precisa ser perceptível sem depender apenas de cor.

Default

Hierarquia normal do componente.

Hover

Pequena mudança de superfície/borda. Não criar animação teatral.

Focus

Outline ≥ 2–3 px com contraste perceptível e offset adequado.

Disabled

Reduz ênfase, mas mantém legibilidade. Não depender apenas de opacidade extrema.

Error

Cor funcional + texto específico + relação explícita com o campo.

Success

Confirmação textual/ícone além de cor.

Loading

Indicar progresso sem bloquear mais interface que o necessário; respeitar reduced motion.

09

Padrões de conteúdo

Componentes técnicos também herdam a voz MotoristaOPS.

Empty state

Dizer o que falta e qual a próxima ação. Evitar ilustração genérica sem função.

Error

Explicar o problema em linguagem humana e oferecer recuperação.

Confirmation

Confirmar o que aconteceu, data/horário quando relevante e próximo passo.

Permission

Explicar por que a permissão é necessária antes de pedir.

Destructive action

Nomear consequência, alvo e possibilidade de reversão. Confirmação proporcional ao risco.

Notification

Priorizar o que muda a decisão do usuário. Não interromper por informação trivial.

10

Motion de interface

Movimento explica mudança, orientação ou continuidade.

Micro

120–180 ms para feedback simples.

Componente

180–240 ms para expansão, entrada curta e mudança de estado.

Layout

240–320 ms quando uma região muda de posição ou tamanho.

Faixas são tokens de referência de implementação; não determinam edição audiovisual. Preferir curvas de aceleração suaves e respeitar prefers-reduced-motion.

11

Acessibilidade de componente

Cada componente precisa ser testado no contexto real. Tokens acessíveis não garantem produto acessível.

Contraste de texto e não-texto atende o mínimo do contexto?
Focus é visível e não fica oculto?
Teclado percorre ações em ordem lógica?
Nome, função e estado são expostos semanticamente?
Alvo de toque atende o piso aplicável e a meta interna?
Erro é identificado por texto, não apenas por cor?
Zoom/reflow não corta conteúdo essencial?
Movimento respeita redução de movimento?
12

Implementação

Os arquivos do pacote servem como base técnica, não como biblioteca de produção já testada em todos os frameworks.

<link rel="stylesheet" href="tokens/tokens.css"> <link rel="stylesheet" href="assets/components.css"> <button class="mops-btn mops-btn--primary"> Falar pelo WhatsApp </button> <section data-mops-theme="dark" class="mops-ui">...</section>

CSS

Variáveis prefixadas com --mops-. Tokens semânticos devem ser usados antes de valores literais.

JSON

Base DTCG 2025.10 para interoperabilidade. Aliases/temas podem ser transformados por pipeline da aplicação.

13

Governança técnica

Componentes também possuem ciclo de vida.

Stable

Uso geral aprovado.

Experimental

Uso controlado; sujeito a mudança.

Deprecated

Não utilizar em novas implementações; caminho de migração documentado.

Definition of Done do componente: função definida, tokens canônicos, light/dark, estados, responsividade, teclado/focus, documentação, exemplo, teste no produto alvo e ausência de conflito com Brand Book.
Design System V2

O código pode mudar de framework. Os papéis semânticos e os princípios não mudam com a ferramenta.

Nota: este pacote define fundação e referência de implementação. Não afirma que uma biblioteca de componentes em produção já foi testada ou implantada.
